# The gate's threat model

This is the one place that says what `hooks/scripts/maude-gate.sh` promises and what it does not. The gate source, `SECURITY.md` and every review of the gate point here. If a finding and this page disagree, the page is changed first, on purpose, and then the code.

## Who the gate is for

The gate catches Claude typing a destructive command by mistake: a force-push, a hard reset, an `rm -rf` on a root, a glob or a sole copy, a history rewrite, a public publish, a write to the red-clear token. It reads the command text a `PreToolUse` hook is handed and refuses before the command runs.

It is not a sandbox. A hook sees text, not what the shell will do with it. The walls that hold against a command built to get past the gate are Claude Code's permission mode, its auto-mode classifier, the harness deny rules, and the account owner's own `!` line. The gate sits in front of those, not in place of them.

## Three tiers

Every review of the gate files each finding into one tier before it reports a severity.

**Tier A. Promised.** A gated command in its plain form, the way Claude types it: the command word spelled out, flags and target as literal words, alone or joined to other commands by `;` `&&` `||` `|` or a newline, behind an env assignment or `sudo`. If the gate passes one of these, the finding is BLOCKING.

The gated commands are the keys in the gate's pattern tables: `force-push`, `git-push`, `reset-hard`, `commit-amend`, `filter-repo`, `filter-branch`, `no-verify`, `no-gpg-sign`, `public-publish`, `rm-rf-root`, `rm-rf-glob`, `rm-rf-sole-copy`, `sole-copy-target`, `sudo-rm-rf`, `drop-table`, `red-self-clear`, `redclear-write`.

**Tier B. Caught when the parser sees it, not promised.** A gated command dressed in shell syntax: a quoted or escaped command word (`"rm"`, `\rm`, `r\m`), brace expansion (`g{it,} push`), a wrapper the gate knows (`bash -c '...'`, `env`, `timeout`, `xargs`), `~` and `$HOME` and `${HOME}` in a path. The gate catches what its parser can read. A miss here is MAJOR: fold it if the fix is small and changes nothing in tier A, otherwise name it as a residual and ship.

**Tier C. Out of scope by construction.** Anything whose meaning only exists when the command runs: a variable's value (`rm -rf $x`), `eval "$x"`, a relative path after `cd`, a script written to disk and run later, an encoded payload, an interpreter call (`python3 -c ...`), an alias or function the gate cannot see. A finding here is a named residual. It never blocks a merge, and the gate does not grow code to chase it.

## The false-block contract

A gate that blocks ordinary work gets switched off, and then it protects nothing. So a false block is held to the same bar as a miss:

- A command that only **mentions** a gated command must pass: a heredoc body written to a file, a commit message, an `echo`, a note, a doc. Blocking one of these is BLOCKING.
- A body that the shell **runs** is a command, not a mention: a heredoc fed to `bash`, `sh` or another shell, or a body written into a file the same command then runs. The gate reads the first; the second only its red backstops read (a named residual, below).
- When the gate cannot tell which one it has, it refuses (fails closed) and says why. That refusal is MINOR unless it fires on work Claude does every day, which makes it MAJOR.

## The stop rule for a review round

A round is clean when it has no tier A finding, no false-block BLOCKING, and every tier B and C finding is written down as a residual by tier. A clean round merges. The next round is the account owner's call, not a reflex. A hostile review over a gate like this can always find another corner. This page is what tells the reviewer which corners count.

## How the gate reads a command

The gate reads command text with regular expressions over several cleaned-up views of it. Its "Known limitations" block lists where that falls short. The parser in `maude_shell/` (design: `docs/specs/2026-10-23-shell-parser-design.md`) reads a command the way bash tokenizes it, and since the wiring branch `maude_shell/judge.py` judges those words beside the regex. Either one blocking blocks: the judge can add a block and never remove one. When python3 is missing the regex verdict stands; when the judge cannot read a command whole, the regex verdict stands and a yellow token is refused (below).

The judge covers the keys whose meaning is in one command's words: `git-push`, `force-push`, `reset-hard`, `commit-amend`, `filter-repo`, `filter-branch`, `no-verify`, `no-gpg-sign`, `public-publish`, `rm-rf-root`, `rm-rf-glob`, `sudo-rm-rf`, `rm-rf-sole-copy`. For those, tier B is what the parser reads: a quoted or escaped command word, brace expansion, the wrappers it knows (`command`, `exec`, `env`, `sudo`, `doas`, `nohup`, `setsid`, `time`, `nice`, `ionice`, `timeout`, `stdbuf`, `xargs`, `busybox`, `uv run`), keyword structure, substitutions, `~` / `$HOME` / `${HOME}`, and a payload a shell runs (`sh -c`, `eval` of plain words, a heredoc or here-string or `echo … |` fed to a shell). `red-self-clear`, `redclear-write`, `drop-table` and `sole-copy-target` stay on the regex alone.

A command is keyed by its most severe hit, not its first. A clear token is per key, and Claude may mint a yellow one, so a command keyed yellow that also held a red key (`git push; \rm -rf /`) passed whole on a yellow token (the commit security review on `965d025`; it held on main too, where the tables stopped at their first row). Now the judge reports every key it reads, the tables rank within themselves, and every stage of the gate (tables, the three red backstops, the judge, the wrapped walk) keeps reading until the key is red. A red key replaces a yellow one; a yellow key never replaces anything. `red-self-clear`, `redclear-write` and `parser-depth` rank red: none is in the red list and no clear script mints them, and their tokens are read from the red file only, because `care.json` is a file Claude can write (lens on `25c9ad2`, MAJOR-1: a token written there for `redclear-write` opened a write to the red file, and with it any red key).

Text that does not parse is still bash that runs: bash runs every complete line before a later syntax error, so one appended `(` once hid a red line above it from the judge (lens on `25c9ad2`, BLOCKING-1). The judge does not try to read such text in pieces (two rounds of a chunked re-read each opened new holes: a quadratic cost that outran the 2 s cut, and a cut that dropped a red hit it had read; lenses 2 and 3). Instead, a command is **not read whole** when:
- its text does not parse;
- a payload body it runs does not parse;
- a payload body is known only at run time (`bash -c "$x"`, `eval "$x"`, `bash $x -c …`, a run-time here-string or `echo … | bash`);
- a shell reads a pipe from anything but `echo`/`printf`/a heredoc (`curl … | bash`), or reads a file on stdin;
- a payload sits past the depth cap;
- the judge was cut, failed in any way but a missing python3, or did not run because the hook had under a second left (it is given only the time left, at most 2 s; lens 3 on `652bbd9`, BLOCKING-1: a padded 125 KB command ran the hook past its 5 s, and a killed hook blocks nothing);
- the wrapped-payload walk stopped on the walks' 3 s clock (lens 4 on `13c95f8`, BLOCKING: a hundred small `bash -c` payloads behind a yellow key ran the hook past its 5 s).

A command not read whole is refused its yellow token, because the unread part may hold a red key. Text nested deeper than the reader's cap is valid bash it cannot read at all, and blocks as `parser-depth`, which nothing clears. A table walk of the live command cut by the gate's clock (3 s of its 5; `fix/gate-time-budget`) blocks the same way as `parser-budget`: the tables are the first reader, and a walk that stops before its last pattern has read nothing it can vouch for, so it refuses rather than runs out. Before that branch, 100,000 spaces before `git push`, 60,000 words then `;`, or 130,000 `;` under the 128 KB cap ran the hook past the harness's 5 s kill, after which a killed hook blocks nothing; one bash substitution over a 100 KB segment was most of it. Every walk over the command is now linear in its bytes (and no run in a pattern row crosses a `;` `&` or `|`, since a run that could scanned to the next space from every start and one grep over 80 KB of `a=1;` cost 45 s, which no clock between patterns can cut: `fix/gate-push-label`), a run of 64 or more spaces, or of tabs, is read as one before any view is made (one class at a time: `<<-` strips leading tabs only, and a mixed run squeezed to its first blank closed a body for the gate that bash kept open), and the clock is asked between patterns and every 64 segments. The cap bounds the bytes the gate reads, not the bytes of the command: `~` is one byte in the command and the home directory's length in every expanded view, so 62,000 tildes under the cap made 600 KB of views and outran the kill in the stages past the clock (the lens on `177319d`); a command whose home-expanded view passes the cap is refused whole, and the red-clear fold, which substitutes a literal value into every use, is bounded as a whole (OVER past twice the cap), not only per word. Cost, named: a command of some 40,000 segments, or one that outruns the clock on a slow box, is refused red; split it. The judge is under the same rule (`fix/gate-push-label`): a judge the clock cut, or skipped for want of time, on a command the tables did not key blocks as `parser-budget` too. Before that, a cut judge added nothing, so a quoted `"git" push` or `env -C <dir> git push`, which only the judge reads, passed whenever the judge was cut, as it was under a loaded suite. A judge that started reading and died (its first line, "read", is on stdout, asked for by the wrapper) blocks the same way, and so does a judge that read the command and could not read all of it when the tables keyed nothing (`parser-unread`): "unreadable" once refused a yellow token and nothing else, and one unread line ahead of a key only the judge reads passed. A payload known only at run time (`eval "$x"`, a shell fed by a pipe) is "opaque" to the judge, not unreadable: it refuses a yellow token, and the wrapped-payload walk whispers and passes it, as it always did. A literal body that does not parse is unreadable at whatever depth it sits; unreadable wins over opaque. A judge that cannot start (no python3, or one that exits with nothing said) is the soft dependency it always was, and the tables' verdict stands: on such a box the shapes only the judge reads are tier B, as they were before the judge. The walk's clock and the judge's budget are read by the real clock, and the judge under budget always has one second, so it is done by 4 s of the hook's 5; a walk of 3 s is refused on a slow day as on a fast one, and the refusal says to retry.

A word known only at run time where the command word stands (`$x git push`, `${x:-} rm -rf /`, `$1 gh release create v1`, `$(true) git push`, a backtick), among git's options (`git $x push`), glued to the verb (`${x}git push`, `gi${x}t push`, `${x}rm -rf /`, `git pu${x}sh`), or in a wrapper's option or operand slot (`timeout $x 5 git push --force`, `sudo $x -u root rm -rf /`, `git -C $x . push --force`) is read as bash runs it when the word comes out empty: the word is gone, a glued word is its literal residue (the parser's empty reading of each word, `$SHELL` and `$BASH` kept), and the slots shift. The judge reads every command more than one way: consumed (each word fills its slot) and vanished, and, since two run-time words before the verb can be one empty and one not (`$x sudo -u $u rm -rf /` with x unset and u set runs `sudo -u <u> rm -rf /`), the run-time words the walk reads before the verb by their kind: a bare one, where a command word stands, empty in every view (filled, it is a wrapper the reader cannot see: opaque); a slot one, an option's value or an operand, empty or filled; one among a wrapper's options, or git's, empty or an option that takes the next word; a value glued to its option or inside an assignment a slot too, the read whole; in every combination up to four such words (past four the read is unreadable, refused when nothing keys), the region read again with the words found so far empty, and with each option-area word taking the next word, until no new one appears (a word discovery cannot place leaves the read unreadable), and keys every hit of any reading; the tables take a run-time word, or a run of them, as a transparent prefix, a `${…}`, `$(…)` or backtick glued to a verb as the path prefix they already skip, and a run-time word among git's global options as skipped. A read in which a run-time word stood where the command word stands, or among git's options in any reading, is never called whole: it is opaque, a yellow token does not open it, since the word can be a wrapper or an alias that changes what runs; one a slot consumed as an option's value or an operand is whole, as before (its value is tier C: a value may split into more words, and that is not read). The block line prints the words as typed (`$x git push`, the whole command when the hit was found with a word emptied) on every path the judge read; a RED the tables keyed on their own prints the tables' message. Before `fix/gate-dynamic-command-word` (2026-11-05) the judge's unwrapping returned "no command here" for a run-time command word and said *pass*, and every key passed behind it, the RED ones too; its first cut read the command word but let an operand slot consume the word (the lens on `4b3cd91`). Cost, named: a command led by `$CC`, `$PYTHON`, `${CROSS}gcc` or a quoted `"$VENV/bin/python"` passes as before and is never read whole; a yellow key beside it waits on the prefix being written out. A default value (`${x:-git} push`) stays tier C: its residue is empty, and what the default says is a value, not read. With no python3 the tables cover the plain forms named in the CHANGELOG; `gi${x}t push`, a run-time word before a wrapper or in a wrapper's slot, and the older `sudo`, `time`, `!`, `{` before a verb are the judge's alone (tier B). A here-string holding an expansion (`bash <<<"$x git push --force"`) is read by neither reader (tier B, older than this change). The fourth lens on that branch

A `git-push` block names the class of remote the push aims at, read from the remote's push URL on the block path only: an internal remote (a local path or `file://`, localhost, a loopback or RFC1918 address, a host under a private suffix, or a host listed in gate-config `internal_push_hosts`), a PUBLIC one (a known public forge), or one the gate could not class, which reads as public. The label is wording; the block and its `git-push` token are the same for every class. It downgrades the wording only on a positive read of a push the gate can place (one push, at the front, in the hook's cwd or a plain `-C`, to the remote git would choose: the command's positional, else `branch.<b>.pushRemote`, `remote.pushDefault`, `branch.<b>.remote`, else origin, a URL taken wherever a name goes) in a command with nothing that could move the push before it runs: a `-c` config override (`url.<base>.pushInsteadOf`), a `GIT_*` or `HOME=` assignment, `cd`, `env`, `--git-dir`, `--work-tree`, `--receive-pack`, an expansion, more than one push. The host is all it prints: a token in an `https://user:token@host` URL never reaches stderr. A URL that can be read two ways (`https://github.com?@x.lan/r`) is read neither way, and a push that recurses into submodules is not placed, since each goes to its own remote. Force-push keeps its red row on every remote. The gate's own read of the remote is a `git remote get-url --push` in a directory the hook input names, under a name the command names: what that config says is what the label says, and a repo whose config was rewritten to lie about its remote lies to the label as well as to the person; the block still stands.

Costs, named: a yellow-keyed command with a syntax error or a run-time payload (`git push; bash -c "$x"`), and a commit message that trips a red backstop (`drop table` beside `psql`, a quoted red clear line, a redirect into the red file), are blocked even with a yellow token; the backstops used to run only when nothing had matched. Since `feat/gate-bypasses`: a shell reading a stdin the judge cannot see (`git push; bash`) is not read whole, so its yellow token is refused; `find` from `/` or a sole copy that deletes with no test (`find / -delete`) is the `rm -rf` it is; and a command handing the reader more than 128 payloads, or more than 400k characters in all, is `parser-depth`, which nothing clears.

Residuals, named, all tier B (each needs a dressed form the tables cannot see, plus text the parser cannot read):
- **A command not read whole, with no key, passes with no token.** When nothing in the tables matches, the tables' verdict stands, as it did before the judge. A dressed red line in such a command (`\rm -rf /` on a line before a syntax error, or in a run-time payload, or with the judge cut) runs. The refusal above protects only a command that already holds a key. The account owner's ruling, 2026-10-24: leave it as a residual.
- **The reader rejects bash that bash runs.** `@(…)` after `shopt -s extglob` is one known case: the parser reads it as a syntax error, so the command is not read whole. Same outcome as the residual above.
- **Feeds and wrappers the judge does not read** (lens 3 on `652bbd9`): other shells' option grammars (`fish`, `tcsh`; bash's `-s`, `+X`, `-o`/`-O`/`+o`/`+O` values and `--rcfile`/`--init-file`, and a `-c` program placed after option values, are read since lens 4 on `13c95f8`), and wrappers not on the judge's list. Read since then:
  - an echo or printf into a shell, its options, formats and wrappers, and `env -S`/`xargs` in front of it (the judge fuzzer, `feat/judge-fuzz`); the read is never whole, so a yellow token does not open it;
  - on `feat/gate-bypasses` (2026-10-31, the account owner's "do the bigger list of bypasses as well"): `|& bash`; the text that reaches a shell through `cat`, `tee`, `head`, `tail`, `sort`, `uniq`, from `echo`, `printf`, `yes`, a heredoc or a here-string; a shell or `source`/`.` reading `/dev/stdin`, `/dev/fd/0`, `-` or `<(…)`, and `sh < <(…)`; `xargs` in front of a shell; `$SHELL`/`$BASH` as the command word; the wrappers `strace`, `ltrace`, `unshare`, `pkexec`, `systemd-run`, `nsenter`, `setpriv`, `runuser`, `chrt`, `taskset`, `chroot`, `flock`; the text carried by `su -c`, `runuser -c`, `script -c`, `flock -c`, `watch`, `trap`, `ssh HOST`; `find … -exec/-execdir/-ok … {}` and `find … -delete`; `git -c alias.NAME=…` run as `git NAME`. Each reads to the key its inner words carry.
- **Encoded or transformed text into a shell** (tier C): `base64 -d | sh`, `tr …`, `sed …`, `rev`, `xxd -r`: the shell runs bytes the judge would have to decode or compute. Not read.
- **A heredoc on a command that changes it before a pipe to a shell** (`tr a-z A-Z <<'E' | bash`, `sed … <<'E' | sh`): the judge reads the heredoc's text as the program, though the shell runs the changed text.
- **A heredoc written to a file the same command then runs** (`cat <<'E' > /tmp/a.sh … bash /tmp/a.sh`) is read only by the red backstops (the red clear lines and the red file), not by the tables or the judge, contrary to what the false-block bar above once said.
- **The token spend can key differently from the reservation.** PostToolUse runs the gate again to spend the token. If one of the two runs is cut and the other is not, they can name different keys, and the reservation is left unspent.
- **Two keys of the same tier share one token.** `git push; git commit --amend` passes on a `git-push` token.

A yellow token opens only a command that was read whole and whose every key is yellow. Two red keys still need the human's hand once.

Named residuals of the judge, by tier:

- **B, not read.** A glob that only matches a sole copy (`rm -rf /work/proj*`); a wrapper option the judge does not know to take an argument; `--help` given as an option's value (`git commit -m --help --amend`); git aliases from a config file (`-c alias.*` on the command line is read).
- **C.** Everything the threat model already puts there: a variable's value, a `cd` before a relative delete, a script written and run later (and a plain `source file.sh`), an interpreter (`python3 -c`, `perl -e`), an alias or a function, encoded text into a shell.
- **Another shell.** The reader models bash. Claude Code may hand a command to zsh (macOS), and tier B is not promised there: zsh reads some quoting, globbing and `=word` expansion differently. The regex tables are no better there; this is named, not chased.
